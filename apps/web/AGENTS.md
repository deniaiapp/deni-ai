# Agent guide for deni-ai (apps/web)

This app is `@deniai/web` in the deni-ai monorepo; read the root `AGENTS.md`
for the workspace layout. Paths below are relative to `apps/web/` unless they
say otherwise; run app commands from here or with `pnpm --filter @deniai/web`.

pnpm, Node.js 26+, TanStack Start (TanStack Router, Vite, Nitro), React Compiler,
strict TypeScript, Tailwind v4, shadcn/ui, Drizzle/Postgres, and better-auth.

## Task boundaries

Complete the requested change and relevant verification, fixing issues caused by
the change before handing it back. Routine local edits and checks do not need
additional approval. Ask when missing information affects scope or an external
action is not already authorized.

Keep changes scoped. Preserve unrelated work. Do not add heavyweight dependencies
or change the toolchain without approval. Do not commit or create branches unless
requested; see the Git policy below.

## Sources of truth

Read these when relevant rather than loading the whole project:

- Commands and dependency versions: `package.json` (pnpm required). The
  lockfile, `pnpm-workspace.yaml` (overrides, build allowlist), shared
  `tsconfig.base.json` and oxlint/oxfmt configs live at the monorepo root.
- Environment validation: `src/env.ts`; setup: `.env.example` and `SETUP.md`.
  Optional empty strings are treated as unset. Never hardcode secrets.
- Database: the Drizzle schema lives in the `@deniai/db` package
  (`packages/db/src/schema/`, `packages/db/drizzle.config.ts`; generated SQL:
  `packages/db/migrations/`). `src/db/schema.ts` re-exports it as `@/db/schema`;
  `src/db/type-registry.ts` types its app-owned JSON columns. The `db:*` scripts
  here forward to `@deniai/db` and still read this app's `.env*` files. Runtime
  uses a pooled Postgres URL (`src/db/drizzle.ts`).
- Chat transcripts: `chats.messages` (jsonb) is still written first, and every
  write also syncs `chat_messages` (one row per message) in the same
  transaction through `src/lib/chat-message-rows.ts`. Add new transcript writes
  there too; reads go through `readStoredMessages()` (rows, or jsonb for chats
  with `message_count` NULL). Backfill: `scripts/backfill-chat-messages.ts`.
- Two-factor rule for password accounts: `src/lib/two-factor-policy.ts`
  (`PASSWORD_2FA_REQUIRED_FROM`), enforced in the `/_app` route guard.
- Auth: the Better Auth configuration is `createAuth()` in the `@deniai/auth`
  package (`packages/auth/src/server.ts`); `src/lib/auth.ts` calls it with this
  app's env, database, email sender and callbacks (sign-up policy, security
  activity, team billing). The client plugins are `createDeniAuthClient()`
  (`packages/auth/src/client.ts`), instantiated in `src/lib/auth-client.ts`.
  Change the client baseURL only when requested. `vite.config.ts` and
  `vitest.config.ts` dedupe the Better Auth packages (`@deniai/auth/dedupe`) so
  the app and the package share one instance. `pnpm run auth:generate` reads
  `src/lib/auth.ts` and overwrites `packages/db/src/schema/auth-schema.ts`.
- Shared code this app imports from workspace packages (read their READMEs):
  model catalog, plan access and token multipliers `@deniai/ai/models`
  (`packages/ai`); email templates `@deniai/emails/<template>`
  (`packages/emails`; sending stays in `src/lib/email.ts`); locales and
  message extraction `@deniai/i18n` (`packages/i18n`; catalogs stay in
  `messages/`); UI components `@deniai/ui`; schema `@deniai/db`; billing rules
  `@deniai/billing`; the usage engine `@deniai/billing/server` (reserve, settle,
  recover, summary, team usage policy, Max Mode credit spending, product ledger),
  which `src/lib/usage.ts` binds to this app's database, billing switch, Stripe
  auto top-up and recovery job. Flixa (services/agent-api) uses the same engine,
  so change usage rules in `packages/billing`, not in `src/lib/usage.ts`.
- Task-specific workflows: `.agents/skills/`; load only the applicable skill and
  references.

## Project conventions

- Match neighboring code: named exports where practical, kebab-case files, and
  `@/*` imports. Keep TypeScript strict.
- File routes (pages, layouts, server routes): `src/routes/` — every file there
  becomes a route, so keep helpers elsewhere. HTTP handler logic: `src/server/`,
  imported lazily from server routes (`async ({ request }) => (await
  import("@/server/http/...")).POST(request)`) so the route tree does not load every
  endpoint's dependencies on the first request; shared components:
  `src/components/`; reusable logic: `src/lib/`; hooks: `src/hooks/`.
  `src/routeTree.gen.ts` is generated by `pnpm dev`/`pnpm build`.
- Code is isomorphic: route loaders and components run on the server and in the
  browser. Keep DB, auth, and secrets inside `createServerFn` handlers or server
  routes; `src/start.ts` holds request middleware (locale and auth redirects) and
  `vite/route-rules.ts` response headers and fixed redirects.
- Navigation: TanStack Router (`@tanstack/react-router`), or the href-based
  helpers in `src/lib/navigation.tsx` for links built from strings.
- Keep edits to generated `src/components/ui/` minimal and API-compatible.
- Use `use-intl` `useExtracted()` for user-facing copy in components, and
  `const t = getExtracted(intl)` from `@deniai/i18n/extracted` in route `head`,
  loaders, and server code. The `@deniai/i18n/vite` plugin (`packages/i18n`,
  registered in `vite.config.ts`) compiles inline messages to catalog keys and
  rewrites `messages/en.json`; keep `messages/ja.json` keys
  synchronized, preserving placeholders and ICU syntax. Avoid locale-conditional
  copy when translations can express it. `/ja/*` URLs render public pages in
  Japanese through the optional `{-$locale}` route param.
- Update related documentation when changing user-facing behavior, environment
  configuration, deployment, or architecture.
- Respond in the user's language; write code and identifiers in English.

## Design system and the UI switch

- The signed-in app uses the "Aizome" design system described in the root
  `docs/design-system.md` (colour roles, type scale, radii, layout, screen
  inventory). Read it before restyling a screen.
- Tokens live in `src/styles/globals.css`: the next UI on `:root` / `.dark`,
  the previous UI under `:root[data-ui="legacy"]`; theme presets
  (`src/styles/themes.css`) apply only under legacy. Use semantic classes
  (`bg-background`, `text-muted-foreground`, `bg-highlight`, `rounded-card`,
  `rounded-field`…) instead of palette colours; for a difference between the
  two UIs use the `next:` / `legacy:` variants. Token changes must keep
  `src/styles/design-tokens.test.ts` (WCAG contrast) green.
- The sidebar is an inverted token island (`[data-slot="sidebar"]`): semantic
  classes inside it already resolve to on-indigo values.
- Page structure comes from `@deniai/ui` primitives: `PageHeader`,
  `PageSection` (settings rows), `SettingsLayout` (`src/components/settings-wrapper.tsx`
  wires the nav) and `AppHeader`. Settings pages render through
  `SettingsPageShell`; `/account/*` renders inside the app shell too.
- `ui` preference: the `deni-ui` cookie (`next` | `legacy`, default `next`) read
  by `src/lib/ui-preference.ts` in the root route, rendered as `<html data-ui>`
  and switched in Appearance settings. Layout changes exist only in their new
  form; legacy restores colours, type and radii.

## Run mode (Deni Run)

Run mode lives under `/run/*` and is entered from the sidebar's chat / Run switch
(`src/lib/app-mode.ts`). Its history and data are separate from chat: the `run_*`
tables of `@deniai/db`, read and written only through `@deniai/run`.

- Pages: `src/routes/_app/run/**`; components: `src/components/run/**`
  (`RunSidebarContent` fills the sidebar body in Run mode; the shell itself is shared).
- API: one catch-all server route, `src/routes/api/run/$.ts`, lazily loads
  `src/server/http/run/router.ts`, which authenticates the web session (guests are
  refused), rate-limits chat and calls `@deniai/run` (streaming chat:
  `handleChat` from `@deniai/run/chat/route`, used with AI SDK `useChat`). The MCP
  OAuth callback is `/api/run/mcp/oauth/callback`.
- Wiring: `src/lib/run/runtime.server.ts` calls `configureRun()` once with this app's
  `db`, the usage engine's `getRunBudget` / `recordRunCost` (`src/lib/usage.ts`) and
  `loadRunConfig(process.env)`. Optional providers (OpenRouter, Exa, E2B, Steel,
  S3/R2, Slack MCP, Discord) are read from env (see `.env.example`); without them the
  UI shows a disabled state instead of failing.
- Background work: `RUN_SCHEDULER_IN_PROCESS=true` runs the job scheduler inside the
  web server (`src/lib/run/in-process.server.ts`), with `RUN_DISCORD_ENABLED=true` also
  the Discord bot (`@deniai/run/discord/*`, discord.js stays a traced dependency). Only
  for one web instance; otherwise `services/run-worker` runs them. The Nitro plugins in
  `src/server/nitro/` start the app at boot (`startup.ts`: one internal request loads
  `src/server.ts`, which awaits `register()`) and run `src/lib/shutdown.server.ts`
  handlers on SIGTERM (`shutdown.ts`): the scheduler stops claiming and waits up to
  `RUN_SHUTDOWN_TIMEOUT_MS` (default 8 s) for running jobs, then the bot disconnects.
- Off switch: `RUN_ENABLED=false` hides the sidebar's mode switch (`authState.runEnabled`),
  redirects `/run/*` to `/chat` in the `/_app` guard and answers `/api/run/*` with
  404 `run_disabled`, and the in-process scheduler does not start. The data stays; stop
  `services/run-worker` separately if one runs.
- Usage: Run spends the shared pool through the engine (model cost as reported,
  browser $0.10/h and computer $0.15/h by default); teammates per plan come from
  `@deniai/run/billing/plans`.
- Migration from the standalone Deni Run: `docs/run-migration.md` at the repository root.

## Private beta (v8 on beta.deniai.app)

v8 runs as a private beta next to v7 (deniai.app) on the same production
database; the rollout and the coexistence rules are in `docs/v8-beta-rollout.md`
at the repository root.

- `BETA_ACCESS_REQUIRED=true` turns on the gate (default off). Access: verified
  admins (`isVerifiedAdmin` + `ADMIN_EMAILS` / `ADMIN_EMAIL_DOMAINS`) or a
  `beta_access` row (by user id, or by verified email, linked on first match);
  with `BETA_ACCESS_PAID_PLANS=true`, also any paid plan (`isOnPaidPlan`);
  never guests. Logic: `src/lib/beta-access.server.ts`; paths and constants:
  `src/lib/beta-access.ts`; admin page: Settings > Beta testers
  (`betaAccess` tRPC router).
- Server enforcement is the `betaAccessGate` request middleware in `src/start.ts`:
  every `/api/*` route is gated (403 `beta_access_required`) unless
  `isBetaGatedServerPath` lists it as open, so a new endpoint is closed by
  default; add a route there only if it must serve uninvited users. Server
  functions are not under `/api`: one that reads or writes user data calls
  `hasBetaAccess()` itself (see `src/routes/_app/projects/$id.tsx`). Pages:
  the `/_app` guard sends uninvited users to `/private-beta`.
- While v7 shares the database, schema changes are made only in
  `packages/db` here, stay additive, and v7 must not generate migrations.
  `CRON_ENABLED=false` and `STRIPE_WEBHOOK_ENABLED=false` keep the beta from
  running jobs and webhooks that v7 already runs.
- `src/lib/version.ts` holds the version and the codename placeholder. Beta-only
  UI (the sidebar "Beta" label and the account menu's "Go to Deni AI v7" item)
  follows `platformCapabilities.privateBeta`, which is
  `BETA_ACCESS_REQUIRED`, so turning the gate off at takeover also hides it
  (`docs/v8-takeover.md`).
- While the rollout Worker splits deniai.app between v7 and v8
  (`docs/v8-rollout.md`), `ROLLOUT_SWITCH_ENABLED=true` adds "Switch to the
  previous version" to the account menu (`platformCapabilities.rolloutSwitch`,
  `src/lib/rollout.ts`). "Send feedback" shows in the beta and during the
  rollout: it opens the help center's form with `from=v8`
  (`src/lib/beta-feedback.ts`), so v8 feedback can be told apart from v7's.
  v8's service worker uses its own cache names so the two
  versions do not serve each other's cached pages.

## Native client API (Deni AI Desktop)

The native desktop app (repository `deni-ai-desktop`) talks to this app over
HTTP, without a WebView.

- Sign-in: the OAuth provider (`@deniai/auth/server`). The desktop app is a
  public native client (PKCE, loopback redirect) registered with
  `pnpm run tools:register-oauth-client --native`; it receives an access token
  with the `chat` scope (`@deniai/auth/oauth`).
- Credentials: `getRequestSession(request, { bearerScope: CHAT_SCOPE })` in
  `src/lib/request-session.server.ts` accepts that token as
  `Authorization: Bearer` and returns the usual `{ session, user }` (session id
  `oauth:<token id>`, no active organization), or else the browser session. Only
  tokens with the `chat` scope from a client registered with `chat` count. Use it
  only in endpoints native clients call: `/api/client/v1/*`, `/api/chat`,
  `/api/chat/stop`, `/api/upload-attachment`, `/api/attachments/:id`. tRPC and
  everything else stay cookie-only, so a token never reaches billing, API keys or
  account settings. The beta gate checks bearer requests too.
- REST layer: `/api/client/v1/*` (`src/routes/api/client/v1/$.ts` →
  `src/server/http/client-v1/router.ts`) adapts the tRPC routers through
  `createCaller`; shapes are `@deniai/client-contract` (change them there first
  and regenerate its JSON Schema). `DESKTOP_MIN_CLIENT_VERSION` retires old
  clients with 426 `client_update_required`.

## Verification

Choose checks that establish the changed behavior:

- Documentation/skill-only edits: check formatting, links, and instruction
  consistency; no app build or dev server is needed.
- Code changes: `pnpm run lint`, `pnpm run format`, and `pnpm run typecheck`.
  Review formatter changes for unrelated edits.
- Runtime/UI changes: use an existing dev server or `pnpm dev` and exercise the
  affected route. Use `pnpm run build` for build/prerender/configuration changes.
- Changes to sign-in, chat sending/streaming, public pages or redirects:
  `pnpm test:e2e` (Playwright; needs `E2E_DATABASE_URL`, see `e2e/README.md`).
  Add or update a spec in `e2e/` when such a flow changes.
- Schema changes: `pnpm run db:generate`, then inspect the generated SQL.
  Apply migrations only when requested for the target environment:
  `db:migrate:dev` loads `.env.local`; `db:migrate` loads `.env` (production).
  Do not infer permission to apply migrations or use `db:push` from schema edits.

Report what was checked and any remaining blockers. Rerun affected checks after
fixes; avoid repeating successful checks without a relevant change.

## Git policy

Daily work lands directly on `canary`; `master` is the release target.

When commit/push/PR work is requested, update local `canary` from its remote while
preserving local changes, commit scoped changes with a conventional message, and
push to `origin/canary`. Do not create a feature branch or a PR into `canary`
unless explicitly requested.

After landing on `canary`, reuse or create a promotion PR with base `master` and
head `canary`. Merge it when merge/instant merge was requested. Summarize the
promoted changes and verification. Never force-push shared branches unless
explicitly requested.

Direct commits and pushes to the master branch are allowed if the user gives permission.
